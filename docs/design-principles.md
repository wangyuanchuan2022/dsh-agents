## 1. loop / 阶段状态一律用持久事件水位，墙钟只用于物理时间语义

### 1.1 原则陈述

凡实现「程序进行到哪了」的状态判定——loop 推进、阶段推进、幂等去重、重放拦截、节流冷却——
一律以**事件身份**为准：`sessionId` / `turn` / `seq`、事件下标水位、回合计数、循环计数。

墙钟（`Date.now` / `setTimeout` / `new Date`）只允许用于**真实的物理时间语义**，本仓收敛为三类：

| 合法用途 | 语义 | 本仓实证 |
|---|---|---|
| 超时保护 | 「这次调用卡了太久」——卡死只有物理时间流逝能界定；轮次可能一秒跑完也可能永不返回，事件计数表达不了 | `lib/advisor/aci/loop.js:142`（整次评审墙钟 deadline）、`:214`（单轮调用超时）、`lib/advisor/runtime.js:906`（单次模型调用超时） |
| 退避间隔 | 「失败后等多久再试」——间隔本身是物理等待；重试**次数**身份由循环变量独立承担 | `lib/spawn.js:295`（`attachDelays[i]` 间隔；`:294` 的 `i` 是重试计数身份，二者正交） |
| 轮询调度 | 「无推送源，定时拉」——时间驱动**刷新**而非时间**判定** | `lib/client.js:340-346`（`setInterval` + `document.hidden` 跳过 + 配对 `clearInterval`） |

按状态性质再分两档落法：

- **水位（幂等 / 去重 /「已裁决到哪」）→ 必须持久化的事件身份。**
  重启后重放历史事件，判定结果必须与首次一致；内存变量跨不了重启，
  时钟值更不行（时钟不标识「哪条事件」，只标识「什么时候看的它」）。
- **节流窗口（「刚投递过，接下来 N 回合别再投」）→ 事件计数表达，不用墙钟。**
  「回合」是宿主事件流的自然节拍；用墙钟表达会把用户暂停、机器睡眠、长回合全部算进窗口，
  与「N 个回合内不重复打扰」的真实语义错位。

### 1.2 判据：时钟值是否进入行为因果链

一个时钟调用点是否受本原则管辖，只看一个问题：**这个时钟值会不会改变程序下一步做什么？**

- **会**——出现在 `if` 比较、`AbortController` 触发、调度延迟的因果链上 → 状态判定点 →
  按本原则审查「事件身份能否替代」；能替代而未替代即违规。
- **不会**——只被写入返回值、记录字段、UI 展示，从不被读取比较 → 非状态判定点 →
  本原则不管它（保留墙钟是正确的，见 1.4 反例警示）。

注意判据看的是**数据流**，不是变量名或 API 形态：`setTimeout` 大多是超时语义，
但 `setTimeout(resolve, delay)` 纯作间隔时它只是物理等待的载体（`lib/spawn.js:295`），
真正的判定身份在同行的循环计数里。

### 1.3 本仓正面参照（三处，2026-10-25 于 `master@6d0f71d` 逐行复核）

| 参照 | 位置 | 机制 |
|---|---|---|
| seq 水位门 | `lib/advisor/observer.js:331` | `if (seq <= state.lastReviewedSeq) return false`——advisor 重放拦截是**纯事件身份水位**：命中即拦截、放行即推进水位（`:327-334`），无任何时钟参与。宿主每条事件的 `seq` 就是现成的事件下标，拿它当水位即可，不需要发明新的计数器 |
| -1 哨兵 | `lib/advisor/store.js:90-91` | `EMPTY_SEEN = () => ({ reviewed: [], lastReviewedSeq: -1 })`——水位**持久化**在 seen 文件，跨重启判定一致。初值哨兵是 `-1` 而非 `0`：宿主事件 seq **从 0 起**（`:384-389` 注释逐字解释），取 0 会让重启后第一条 `seq=0` 的事件命中 `0 <= 0` 被**静默漏评**。写水位先钉哨兵语义，是本参照的另一半 |
| 回合计数冷却 | `lib/advisor/delivery.js:86,100-106,150` | advisor 投递冷却是 **Map 回合计数**：投递即武装 `immuneTurns`（`:150`），每个主回合完成递减 1（`:101-106`），会话注销即清除（`:97`）——语义按「回合」走而非「N 毫秒」，是 1.1「节流窗口用事件计数」的落地实例 |

### 1.4 反例警示：展示 / 审计字段不算状态判定

时钟值出现在代码里，最容易被误判的有**两个方向**：

**方向一：把展示/审计字段误当状态判定去「改造」。**
本仓 2026-10-25 时钟盘点命中 27 处，其中 23 处是 B 类非状态判定，全部**合法保留**：

| 形态 | 实证 | 为什么不算状态判定 |
|---|---|---|
| 工具输出时间锚 | `lib/index.js:76-81` `fmtNow`（注释原文「工具输出前置，模型拿它判断新旧」） | 它就是**给模型看的墙钟**——功能本身是「展示物理时间」，换成事件序号反而废掉功能 |
| runtime 审计字段 | `lib/advisor/runtime.js:623` `this.lastAt = Date.now()` | 读点只有状态快照与 UI「上次 HH:mm」（`lib/client.js:467` 经 `formatTime`（`:261-265`）渲染），**无任何 `if` 比较**；换事件序号会破坏用户可读契约且零判定收益 |
| 落盘审计戳 | `lib/advisor/store.js:104` `createdAt` 缺省 `Date.now()` | 记录消费按 `sessionId` 过滤 + 条数截取，幂等门是 `(sessionId, turn, seq)`；`createdAt` 不参与判定 |
| 命名素材 | `lib/taskbook.js:172-175` `stamp` 产出文件名后缀 | 时间在这里只做**唯一化命名**；撞车判定本身是 `existsSync` 存在性检查（`:183`），不是时间判定 |

**方向二：把真实状态判定伪装成「只是展示」。**
反向错误更危险：给时钟值起个 `lastAt` / `recordedAt` 之类的审计感名字，实际却拿它做 `if` 比较——
变量名骗得了 grep，骗不了数据流。判据永远回到 1.2：**看时钟值是否进入行为因果链，不看它叫什么。**
（同族陷阱：用「上次触发时刻 + 间隔阈值」实现节流，本质是墙钟状态判定，应改事件计数——
`lib/advisor/delivery.js:100-106` 是正确写法。）

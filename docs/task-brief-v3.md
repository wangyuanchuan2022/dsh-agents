## 1b. 上下文隔离契约（〔生成〕，新增；评审/验证类任务由 `agent_taskbook`/`agent_spawn` 自动写入，本表为口径正本）

隔离分**两层，缺一不可**——只做会话层而材料层泄漏作者结论，仍是假盲评：

| 层 | 由谁保证 | 内容 |
|---|---|---|
| 会话层 | `agent_spawn` | 每席都是**全新 DSH 会话**，不继承组织者对话历史（评审员看不到作者的推理过程） |
| 材料层 | 本表 + 任务书条款 + 机检 | 任务书里**给什么/不给什么**：只给被评审对象（diff/文件/产物）、明确基准（spec/清单/验收标准）；不给作者自评与理由、不给其他席位产出（blind 席） |

隔离模式（`lib/roles.js` 的 `isolationOf()`，按角色自动判定）：

- **`blind`**（`code-reviewer`、`security-reviewer`）：并行盲评席——不得获得 ①作者自评/理由 ②**其他席位**的产出与结论；两席任务书除角色外必须逐字一致。
- **`isolated`**（`critic`、`code-simplifier`、`verifier`）：独立评审/验证席——不得获得作者自评/理由；`critic` 拿到各席报告是设计允许的（它就是解盲点）。
- **`shared`**：其余 14 个实现/协作类角色，不做隔离。

**机检（fail-closed 告警，不阻断但必须显式可见）**：下发材料（正文 + 背景 + 现状盘点 + 交付 + 验收 + 缺省决策表）逐条匹配泄漏模式——`author-rationale`（作者自评/理由）、`peer-output`（其他席位结论，仅 blind 席适用）；命中即以 `⚠️ 隔离泄漏（…）` 点名命中原文，`isolationLeaks` 非空须清理后重派。**污染处置**：若材料里仍出现，评审席须 ① 不引用不采信 ② 报告首行标注「⚠️ 隔离污染：<原文片段>」③ 只以可核验产出、证据与基准为准。

### 5.1 交付状态三值字段（〔生成〕，新增 #2）
汇报时**只能自报前两值**；第三值由组织者/用户确认后才成立：

| 状态 | 含义 | 谁可自报 |
|---|---|---|
| `DELIVERED_WITH_EVIDENCE` | 产出已落盘 + 已广播，证据齐备 | 执行者 |
| `BLOCKED_NEED_HUMAN` | 卡点明确（缺授权/缺参数/上游变更），需人介入 | 执行者 |
| `DONE` | 验收通过 | **仅组织者/用户**——执行者自报 DONE 无效 |

### 5.2 skip 必留痕（〔生成〕，新增 #5）
任何因环境（提权/凭据/平台/网络）而**未执行的检查或步骤**，必须显式记录为 `skipped + 原因 + 复跑命令`，**不得计入通过项**；组织者核验时 skipped 单列。

### 5.3 三层失败分类（〔生成〕，OCR 批次新增）
凡未完成的步骤必须落进对应层的封闭枚举，禁止混用（"没做"与"做失败"必须可分辨）：

| 层 | 含义 | 处置格式 |
|---|---|---|
| attempt 级 | 单次工具调用失败 | 重试计数 +1；连续 3 次按 §6.2 熔断 |
| item 级 | 某对象/文件没处理完 | `skipped(封闭枚举理由)+复跑命令` 或 `blocked(原因+复跑命令)` |
| run 级 | 整场停摆 | `run_failure=<类目>`；已完成部分照常交付 |

> 理由：只有"申报过的限额"才配 budget 类；新增失败原因默认落诚实兜底类，永远不要继承预算/工具限制标签。

### 5.4 回收契约（〔组织者填〕，v3.2 新增 IMP-06）
本轮派活只要 spawn/wake 过任何子会话，就必须在本节留下**可核销的回收计划**——纪律底线：**不为单 agent 能装下的活分层；不派无回收计划的活**（fire-and-forget 委派禁止；"最终消息即交付物"的语义 = 消息本身不构成交付，落盘 + 广播双条件才算）：

| 被派会话（角色/会话ID） | 回收触发点 | 完成核销单 | 超时处置 |
|---|---|---|---|
|  |  |  |  |

- **回收触发点**（封闭枚举，任一即触发回收动作）：① 完成广播（`de_broadcast` 到达组织者收件箱）；② 心跳超时（巡检闹钟到点，主动 `de_session status` + 产出文件 mtime 巡检）；③ 回合上界到达（3 轮无落盘增量的移交清单到达）。
- **完成核销单（双条件，缺一不核销）**：① 产出已落盘——evidence 路径存在且非空（Task-Path 可验证，接受扫描）；② 已广播——完成消息到达（subject 含「<角色id> 完成」）。只落盘不广播 = 未完成；只广播不落盘 = 未完成。
- **超时未回收处置**：按 §8.1 退出码处置（2=查文件后要求补广播或直接验收 / 4=按断点重派带增量指引 / 5=挂待办不判死不重派），并在 §8 回收表登记核销结果。
- **前置硬门**：派活前置三问通过但本表未填 = 派活不完整，响亮失败（回收计划缺失的活不派）。

## 6. 约束与工作纪律
- 只读范围：除报告外禁止改文件 / 禁止 install / build
- 失败重试上限：同一目标 2 次失败即跳过并如实标注
- 收尾自检：交付前跑 format_gate（报告类）或对应验收工具，FAIL 不交付

### 6.1 回合上界与增量指引（〔生成〕，新增 #8）
- **回合上界**：同一步骤在同一会话内最多 3 轮无新落盘增量的往返；达限即收尾，把剩余项列成清单广播移交组织者重划界，不得无限续命。
- **增量指引**：收到唤醒/追加消息时只处理增量指令，不重做已确认的部分；给子会话发续作指令时也只发增量（原任务已在会话历史里，重发浪费且易自相矛盾）。

### 6.2 三档熔断与收尾宽限轮（〔生成〕，OCR 批次新增）
- **三档熔断**：同一动作连续失败的反馈必须改变形态——第 1 次返回原错误（可重试）→ 第 2 次明示"这是第二次连续失败，修参数或交付"→ 第 3 次判"已放弃，不再重试"；成功即清零。重派类任务第 2 次必须显式改写任务书，不许原样重派。
- **收尾宽限轮**：预算收紧后的最后一轮只许提交已识别的产出、不许新开分析面（"最后一轮只能交付"）。

## 7. 验证与裁决
- 验证方式（可机检的写明工具与参数，如 deliverable_verify targets=[...]）：
- 验证失败处理：修复后重验，最多 <2> 轮；仍失败 → 如实上报 blocker
- 争议裁决：分歧按 fail-closed（写操作不动）/ fail-open（读操作先做）判定；结构级分歧升级组织者

### 7.1 断言鉴别力条款（〔生成〕，新增 #4）
涉及解析/分类/闸门/测试类改动时，验收断言必须满足三条硬要求：
1. **多元素断言**：解析/分类类功能至少一个 ≥3 元素输入的断言（单元素断言分不出实现用的是「串接」还是「取首个」，零鉴别力）；
2. **注入必红**：新增闸门必须配负向自测——把典型变异喂进去断言目标闸门变红（只验证好文件过门的闸门是半成品）；
3. **真实样本全量跑**：验收链必须含「真实仓库/真实输入无 workaround 全量跑」一项，不能只跑自造 fixture。

### 9.1 confirmed_findings 块规范（〔生成〕，OCR 批次新增；增量轮结构化下发）
- 格式：序号 + 文件 + 单行 code 摘要（≤200 字符）+ 单行结论摘要（≤300 字符），总量 ≤30 条；
- 附否定式指令："不要重复它们；继续在剩余面上找新发现，不得因清单存在而止步"——该块约束的是**重复**，不是**范围**；
- **免查需凭证**：免查项必须在上一轮覆盖账（verdict.md 覆盖账节）有 reviewed 记录**且**文件内容哈希未变，否则重评。

### 9.2 工作单元状态语义（〔组织者填〕，v3.2 新增 IMP-14；epic 状态语义移植——只取语义不取 GitHub 载体）
多会话并行批次按「工作单元」管理状态。GitHub issue 载体（issue body / gh CLI / SQLite 缓存）不移植，由本模板 + 产出文件 + dtodo 项目轨承载：

**① 工作单元四字段头**——每个工作单元（= 一份子任务书）的登记行头部必备四字段：

```
status=<pending|running|blocked|done>  owner=<会话ID/角色>  evidence=<产出文件路径>  merge_gate=<validate|review|none>
```

**② 依赖与解锁**——依赖用 `deps:[<产出文件>]` **显式声明**（结构化字段，写在任务书「依赖」节）；解锁判据 = 依赖产出文件**存在且非空**（`Test-Path` + 字节数 > 0 即判），会话状态 ≠ 解锁依据（idle 不代表产出可用）。
⚠️ **显式禁止正则扫全文提取依赖**（ECC F-1 教训：对格式漂移零防御，曾把「等依赖」误判成「无依赖」直接开跑）。依赖关系只认声明字段，不许从任务描述文本反推。

**③ 单写者所有权**——一个执行者一个产出文件；**禁止多写者写同一状态文件**（ECC F-2 教训：双重认领互覆盖）。共享状态只由组织者单点汇总（§8 回收表），执行会话只写自己的 evidence 产出。

**④ 状态迁移白名单**（非法迁移视为事故登记——先广播说明缘由，再按登记处置）：

| 迁移 | 合法性 | 条件 |
|---|---|---|
| pending → running | ✅ | 会话已派活且真实开工（de_session status=running **且**磁盘有增量，防应酬式回合） |
| running → blocked | ✅ | 卡点明确且已广播（附退出码 4/5 与复跑命令） |
| blocked → running | ✅ | 阻塞解除（人介入完成 / 依赖就位），owner 不变 |
| running → done | ✅ | §5.4 完成核销单双条件达成 |
| blocked → done | ✅ | 组织者核销（部分产出可收时） |
| done → running | ❌ 非法 | 需重做时新建工作单元，不复活 done 单元 |
| pending → done | ❌ 非法 | 跳过执行面的 done 不可信，一律走 running |

**⑤ publish/收尾前双门**——任何「发布/收尾」动作（合并、交付、关账、push）前置双门 = **validate 通过**（机检可复跑）+ **review approved**（评审席明确 APPROVE，非默认通过）。两门独立，一门不过不收尾；缺门的收尾按 §5.3 run 级失败登记。

**「等谁」的挂起承载**——执行会话等上游产出时**不空转**：组织者把「等 <deps 产出文件> 就绪」写进 **dtodo 项目轨**（target=project，正文注明被等文件路径与解锁判据），由组织者巡检解锁后 wake 执行会话；执行会话自身按 §6.1 回合上界收尾，不无限等待（防「等谁」变成静默挂死）。
